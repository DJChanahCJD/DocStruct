# 第一章 背景

## 1.1 研究背景与意义

软件工程文档是软件生命周期中承载需求、设计、接口、测试等活动信息的关键载体。随着软件系统规模和复杂度的持续增长，项目在需求、设计、测试、运维等阶段产生的非结构化文档数量急剧膨胀。一份典型的中大型软件项目可能涉及上百份需求规格说明书（Software Requirements Specification, SRS）、接口设计文档、测试报告和用户手册。这些文档虽然以自然语言编写、便于人类阅读，但其中蕴含的结构化信息——例如需求条目、接口定义、测试用例——却难以被工具自动化处理。

传统上，从软件工程文档中提取结构化信息依赖人工阅读和手工录入。这种方式存在三个突出问题：第一，效率低下，当文档数量达到数十份时，人工提取所需时间呈线性甚至超线性增长；第二，一致性难以保证，不同人员对同一文档的理解可能存在偏差，导致提取结果不一致；第三，可追溯性差，提取出的结构化数据与原始文档之间缺乏可验证的引用关联，当数据出现争议时难以回溯到原文进行复核。

近年来，大语言模型（Large Language Model, LLM）在自然语言理解与生成任务上展现出强大的能力。LLM 能够从非结构化文本中识别实体、关系、属性，并按指定的结构化格式输出结果。这为软件工程文档的自动化信息提取提供了新的技术路径。然而，直接将 LLM 应用于文档结构化提取面临若干工程挑战：长文档超出上下文窗口限制、提取结果缺乏可验证的证据锚点、不同文档类型需要不同的提取模式等。

DocStruct（Document Structure Extractor）系统正是针对上述问题设计的一套基于大模型的软件工程文档内容结构化提取系统。该系统支持 PDF、DOCX、Markdown、纯文本四种常见文档格式的自动解析，能够识别六种主流软件工程文档类型并采用专用提取模式，通过"分块-并发提取-合并归约"的 Map-Reduce 管道实现长文档的完整覆盖，并为每个提取结果绑定可回溯的证据信息。系统的目标不是替代人工审查，而是提供一个高自动化程度的初提取结果，将人工的角色从"提取者"转变为"校验者"，从而显著提高文档信息化的效率与可靠性。

本课题的工程意义在于：为软件工程团队提供一套可落地的文档结构化工具，降低从遗留文档中恢复结构化信息的成本；其学术意义在于：探索 LLM 在软件工程文档这一垂直领域的提取能力边界，验证 Map-Reduce 管道配合证据绑定机制的可行性与有效性。

## 1.2 国内外研究现状

### 1.2.1 传统文档信息提取方法

在 LLM 广泛使用之前，从软件工程文档中提取结构化信息主要依赖三类方法：基于规则的方法、基于传统机器学习的方法和基于领域特定语言解析的方法。

基于规则的方法通过手动编写正则表达式、关键词匹配和模板规则来识别文档中的特定信息片段。此类方法在格式高度固定的文档（如特定模板生成的 API 文档）上效果较好，但泛化能力极弱，一旦文档风格或模板发生变化，规则往往需要大幅重写[1]。基于传统机器学习的方法利用条件随机场（CRF）、支持向量机（SVM）等模型进行命名实体识别和信息抽取，相比规则方法具有一定的泛化能力，但依赖大规模标注数据，且对文档的结构化上下文利用不足[2]。基于领域特定语言解析的方法，如针对 API 文档的 OpenAPI/Swagger 解析器或针对代码注释的 Javadoc/Doxygen 工具，虽然提取精度很高，但只能处理特定格式的输入，无法应对自由文本形式的软件工程文档。

### 1.2.2 基于大语言模型的信息提取

随着 Transformer 架构和预训练语言模型的快速发展，基于 LLM 的信息提取方法在多个领域取得了显著进展。GPT-4、Claude、DeepSeek、Qwen 等模型在零样本和少样本条件下展示出强大的信息抽取能力，能够从非结构化文本中按指令输出结构化 JSON 或特定格式的结果[3]。

在软件工程领域，已有研究探索使用 LLM 进行需求分类、代码摘要生成、缺陷报告分析等任务。然而，大多数工作聚焦于单一文档类型或单一提取槽位（如仅提取需求条目或仅提取接口定义），缺乏涵盖多种文档类型的统一提取框架。此外，现有研究对以下三个关键问题的关注不足：第一，长文档处理——当文档长度超出 LLM 上下文窗口时，如何保证提取覆盖率和一致性；第二，证据追溯——提取结果的可靠性如何通过可验证的源文档引用加以支撑；第三，分类型提取——不同种类的软件工程文档具有不同的语义结构，如何设计针对性的提取模式。

### 1.2.3 文档解析与结构化预处理

文档解析是 LLM 提取之前的必要预处理环节。PDF、DOCX 等二进制格式的文档需要先转化为文本表示才能输入 LLM。当前主流的文档解析工具包括 PyMuPDF（基于 MuPDF 引擎）、pymupdf4llm（专门面向 LLM 的 Markdown 输出转换）、python-docx（DOCX 格式解析）以及 Docling（IBM 开源的文档理解库，提供更精确的表格识别和边界框坐标提取）[4]。这些工具各有侧重：PyMuPDF 提供基础的文本提取和布局分析；Docling 在表格结构识别和视觉文本合并方面表现更优。在 LLM 驱动的文档处理管道中，解析质量直接影响后续提取的准确度，因此解析后端的选择和容错设计是系统实现中的重要考量。

## 1.3 研究内容与创新点

本文围绕"如何高效、准确地从多种软件工程文档中提取结构化信息并建立证据追溯"这一核心问题展开研究，主要研究内容包括以下四个方面：

**（1）多格式文档统一解析与中间表示构建。** 设计并实现统一的文档解析管道，支持 PDF、DOCX、Markdown 和纯文本四种输入格式，将异构格式统一转化为 Markdown 中间文本表示（Document Intermediate Representation, Document IR）。Document IR 包含元素级结构信息（标题、段落、表格、代码块等）、页面坐标和章节大纲，为后续分块、提取和证据绑定提供统一的数据基础。

**（2）文档类型专用提取架构。** 定义六种软件工程文档类型（SRS、API 设计、系统设计、测试文档、用户手册、问题/缺陷单）的专用提取模式，每种模式包含特定的输出槽位和 Pydantic 校验模式。通过 Phase 0 预扫描机制实现文档类型的自动识别和关键实体发现，使得提取管道能够自适应地选择正确的提取策略。

**（3）长文档 Map-Reduce 提取管道。** 设计并实现基于 Map-Reduce 范式的长文档提取管道：在 Map 阶段，将文档按章节边界分块，并发调用 LLM 对各分块进行局部提取；在 Reduce 阶段，通过确定性算法对分块结果进行合并、去重和全局 ID 分配。该管道有效克服了 LLM 上下文窗口对文档长度的限制。

**（4）提取结果证据绑定机制。** 为每个提取出的结构化对象绑定源文档中的证据信息，包括页面编号、边界框坐标和文本片段。证据绑定使用户可以通过前端界面点击任意提取对象，直接导航到原始文档中的对应位置并查看高亮标记，实现提取结果从"黑盒输出"到"可验证引用"的转变。

本文工作的主要创新点可以归纳为：

- **提出面向软件工程文档的多类型专用提取架构**。区别于通用 JSON 输出模式，为每类文档定义专属的提取槽位和校验模式，并通过预扫描机制自动匹配文档类型。
- **设计 Map-Reduce 管道与证据绑定相结合的处理范式**。将 LLM 的语义理解能力限定在局部上下文，将跨上下文的协调和可追溯性保证交由确定性算法处理，兼顾了提取质量和可验证性。
- **构建完整的端到端系统并开展实证评估**。不仅实现了从文档上传到结构化结果展示的完整管道，还设计了离线评估框架，支持多模型对比实验和消融实验，为 LLM 在软件工程文档提取领域的应用提供实证数据。

## 1.4 论文组织结构

本文共分为七章，各章内容安排如下：

第一章为背景，阐述课题的研究背景与意义，综述国内外研究现状，介绍本文的研究内容与创新点，并给出论文的组织结构。

第二章为相关技术，介绍系统实现过程中涉及的关键技术，包括大语言模型与提示词工程、文档解析技术、分块策略，以及 FastAPI、React、Pydantic 等开发框架。

第三章为需求分析，从系统目标与范围出发，详细分析功能性需求、非功能性需求，定义六种支持的文档类型及其输出模式，并说明系统的数据需求和边界约束。

第四章为系统设计，给出系统的总体架构设计，深入阐述核心处理管道（Map-Reduce）、分块策略、Reducer 合并去重算法、数据模型以及 RESTful API 接口的设计思路。

第五章为系统实现，描述各核心模块的具体实现方式，包括文档解析模块、结构化提取模块、Reducer 与证据绑定模块以及前端界面的实现细节。

第六章为系统测试，介绍测试环境与数据集，定义评估指标体系，开展模型对比实验和消融实验，并对实验结果进行分析与讨论。

第七章为结论，总结全文工作，归纳主要创新点，分析系统存在的不足并提出未来的改进方向。
