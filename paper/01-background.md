# 第一章 背景

## 1.1 研究背景

软件工程文档是软件项目管理和技术交付中的基础资料。需求规格说明书记录系统目标、用户角色和功能约束；API 文档描述接口路径、请求参数和响应格式；概要设计文档说明模块划分、架构风格和核心流程；测试用例文档用于验证功能正确性；数据库设计文档则保存表结构、字段约束和数据关系。这些文档共同支撑软件系统的设计、开发、测试和维护。

在实际项目中，软件工程文档往往由不同人员在不同阶段编写，文件格式和表达方式不统一。即使内容较完整，文档中的关键信息也常以自然语言、表格、编号条目或混合格式存在。人工阅读可以理解其含义，但程序难以直接获取可计算的结构化数据。需求抽取研究指出，从非结构化文本中识别需求本身就是耗时且容易出错的任务，模型需要面对不同来源、不同粒度和不同写作风格的文档[1]。API 文档自动转换研究也表明，真实在线 API 文档常缺少统一结构，人工转换为 OpenAPI Specification 的成本较高[2]。软件配置规范抽取研究进一步说明，软件说明、手册和讨论材料中包含大量规范性信息，但这些信息缺少统一组织，难以直接被工具使用[3]。

PDF 等版式文档还会带来额外的解析困难。相关 PDF 内容提取系统研究关注 OCR、图像处理和版面信息恢复等问题，说明电子文档中的文本并不总能直接按阅读顺序获取[4]。因此，软件工程文档结构化提取不仅需要自然语言理解能力，还需要可靠的文档解析、分块、结果校验和证据回溯机制。

近年来，大语言模型在自然语言理解、摘要生成和结构化输出方面表现突出，为软件工程文档自动解析提供了新的技术路径。大模型能够理解文档中的语义关系，并根据给定 Schema 输出结构化结果。但如果缺少输入分块、类型约束、结果合并和证据回溯机制，大模型输出仍可能出现编造、遗漏、格式错误或难以验证的问题。因此，如何将大语言模型能力与确定性工程流程结合，是本文关注的核心问题。

## 1.2 国内外研究现状

在需求工程领域，Ivanov 等基于 PURE 数据集构建人工标注语料，并使用 BERT 对需求和非需求句子进行分类，说明深度学习方法可以用于非结构化需求识别[1]。ReqFusion 进一步探索多模型供应商和结构化提示在需求分析中的应用，说明需求抽取质量与提示结构、领域分类框架密切相关[10]。该类方法通常以句子或需求项为中心，对需求发现有参考价值，但与本文面向多类型软件工程文档的 typed JSON 抽取仍有差异。

在 API 文档结构化方面，OASBuilder 将在线 API HTML 文档转化为 OpenAPI 规范。该方法将文档抓取、操作分段、无关内容过滤、并行 LLM 调用和人工校验平台结合起来，体现了大模型与规则流程结合的工程化思路[2]。DocStruct 处理的文档类型更广，但 API 文档抽取部分与 OASBuilder 的目标具有相似性。

在软件规范自动合成方面，SpecSyn 使用大语言模型从自然语言来源中合成软件配置规范，并报告相较既有方法在 F1 上有提升[3]。该研究说明，大语言模型适合处理软件文档中的规范性描述，但系统仍需通过 Schema 和校验机制减少不稳定输出。

在文档解析方面，文档智能领域的研究系统梳理了版面分析、信息抽取等核心任务的深度学习模型与基准数据集[13]；Docling 技术报告介绍了面向 PDF 等文档的转换能力，可输出 Markdown 或 JSON，并支持布局分析和表格识别[5]；MinerU2.5 则从高分辨率文档解析角度提出解耦视觉语言模型，为复杂版式文档的布局识别提供了另一种思路[9]。这类工具为本文 Document IR 构建和 PDF 证据定位提供了参考。对于长文档处理，LLM×MapReduce 提出将长序列拆分为多个子任务并聚合结果的免训练框架[6]，与本文的分块 Map 抽取、全局 Reduce 合并思路一致。对于结果可追溯性，ALCE 从流畅性、正确性和引用质量等角度评估带引用生成[7]，Ragas 关注检索增强生成中的忠实度和上下文相关性评估[8]，Core 则从信息性子声明角度提升事实精度评分的鲁棒性[11]。这些工作为本文证据绑定和抽取结果评估提供了启发。检索增强生成研究也表明，将生成结果与外部知识或上下文证据结合，有助于提升知识密集型任务的可验证性[12]。

## 1.3 相关技术基础

大语言模型是一类基于大规模语料训练的自然语言处理模型，能够完成文本理解、摘要生成、信息抽取和格式化输出等任务。本文使用大语言模型处理软件工程文档中的局部语义识别问题，例如从需求段落中抽取功能需求，从接口文档中识别接口路径和请求方法，从数据库设计文档中提取表和字段信息。

软件工程文档常见格式包括 PDF、DOCX、Markdown 和 TXT。Markdown 与 TXT 可直接读取文本，DOCX 需要解析段落与表格，PDF 则可能包含复杂版面、分页、文本层和坐标信息。DocStruct 通过 ParserFactory 按扩展名选择解析器，将不同格式统一转换为 Document IR[5]。

Document IR 是系统内部使用的文档中间表示。它将原始文档转化为元素列表、章节大纲、标题、文档类型和元数据等结构。每个元素包含 element_id、文本或 Markdown 内容、页码、bbox、章节路径和阅读顺序等信息。Document IR 既是分块输入，也是证据绑定的数据来源。

结构化抽取是指从自然语言或半结构化文本中识别目标对象，并输出为机器可读格式。本文采用 Pydantic 定义各类文档的 typed schema，与通用 JSON 生成相比具有更强的稳定性，且不同类型文档之间的抽取逻辑可以复用。

Map-Reduce 是本文抽取流程的核心思想。系统先按章节和元素边界将文档拆分为多个 chunk，对每个 chunk 并发调用大语言模型进行局部抽取，最后将候选结果合并为全局结果。这一思路与长序列处理中”拆分、局部处理、再聚合”的方法一致[6]。

## 1.4 研究意义

本文研究的软件工程文档结构化提取具有以下意义。

第一，提高文档复用效率。将自然语言文档转换为 typed JSON 后，需求、接口、模块、测试用例等对象可以被程序直接读取和分析，减少人工整理成本。

第二，增强结果可追溯性。系统为提取对象绑定原文证据，保留页面、bbox 和文本片段等定位信息，使用户能够从结构化结果回到原始文档检查依据。证据回溯也有助于减少大模型生成内容难以验证的问题[7]。

第三，降低大模型工程化风险。系统将大模型限定在局部语义抽取环节，并使用 Pydantic Schema、Reduce 合并和证据校验约束输出结果，避免完全依赖一次性生成。

第四，为后续质量分析和自动化评测提供基础。结构化结果可进一步用于需求审查、接口一致性检查、测试覆盖分析等软件工程任务。

## 1.5 本文工作

本文围绕 DocStruct 系统完成以下工作。

1. 设计面向软件工程文档的 typed schema，覆盖需求、接口、概要设计、测试用例和数据库设计五类文档。
2. 构建 Parser 到 Document IR 的解析层，将不同格式文档统一为包含元素、章节、页码和证据锚点的中间表示。
3. 设计章节感知分块和 Map-Reduce 抽取流程，使系统能够处理超过单次提示词舒适范围的中短文档。
4. 实现证据绑定机制，将结构化对象与原文元素关联，支持前端对照查看和 PDF 定位。
5. 构建 FastAPI 后端与 React 前端，完成文件上传、后台处理、结构化结果展示和调试接口。
6. 建立轻量人工标注数据集和离线评测脚本，并通过模型对比实验确定最终使用 DeepSeek-V4-Flash。

## 1.6 论文结构

本文共分为六章。第一章介绍研究背景、国内外研究现状、相关技术基础、研究意义和主要工作。第二章给出系统需求分析。第三章说明系统总体设计、数据模型和处理流程。第四章描述系统关键模块实现。第五章介绍系统测试与实验设计。第六章总结本文工作，并讨论不足与后续改进方向。
