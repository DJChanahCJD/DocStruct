# 第二章 需求分析

## 2.1 系统目标

DocStruct 的目标是实现一个面向软件工程文档的结构化提取系统。系统接收用户上传的文档，自动解析原文，调用大语言模型抽取关键对象，并输出带证据回溯的 typed JSON。系统聚焦单文档级别的结构化抽取，不涉及跨文档知识库、向量检索、问答机器人、URL 爬取和多模型在线切换。该边界有助于保持系统目标明确，后续扩展可在当前 typed JSON 和证据回溯基础上构建上层应用。

系统的主要用户是软件工程项目中的开发者、测试人员、项目管理人员和论文实验人员。用户希望通过系统快速获得文档中的需求、接口、模块、测试用例或数据表等结构化对象，并能够回到原文检查抽取依据。

## 2.2 功能需求

系统应支持文档上传。用户可以上传 PDF、DOCX、MD 和 TXT 文件，并在上传时指定文档类型。支持的文档类型包括软件需求规格说明书、API 接口文档、概要设计说明书、测试用例文档、数据库设计文档和未知类型。

系统应支持文档解析。上传后，系统需要读取原始文件内容，生成 raw_text，并构建 Document IR。对于未知类型文档，系统只保留原文、摘要和 IR，不执行结构化抽取。

系统应支持摘要生成。系统在解析后调用大语言模型生成文档摘要，摘要作为后续分块抽取的全局上下文。摘要失败不应阻断结构化抽取主流程。

系统应支持结构化抽取。对于五类主干文档，系统应根据文档类型选择对应 typed schema，按章节感知分块执行 Map 抽取，并通过 Finalizer/Reduce 合并为最终 JSON。

系统应支持证据回溯。每个主要抽取对象应尽量绑定 1 到 3 个原文 evidence_element_ids，最终生成 evidence。证据应包含 object_id、element_id、text_span、page 和 bbox 等信息，其中 page 和 bbox 取决于解析器是否提供坐标。

系统应支持结果查看和人工修订。用户可以查看文档列表和详情，可以修改 raw_text、summary 或 extracted_data。修改 raw_text 后，系统应清除旧的 document_ir，避免 IR 与原文不一致。

系统应支持调试与重试。用户可以查看当前分块规则生成的 chunks 调试数据，也可以对已有文档重新执行结构化抽取。

## 2.3 非功能需求

正确性方面，系统应优先保证抽取结果符合 typed schema，避免输出非法 JSON 或无约束字段。对于大模型输出，应进行解析、归一化和 Pydantic 校验。

可追溯性方面，系统应保留原文、摘要、Document IR、抽取结果和证据记录，使结构化对象能够回到原始文档检查。

可维护性方面，系统应将不同职责拆分为 Parser、IR、Chunker、Extractor、Reducer、Schema Registry 和 API 服务等模块。新增文档类型时，应优先通过新增 schema 和注册映射完成，而不是修改大量管道逻辑。

性能方面，系统面向中短文档，默认最大字符数为 100000。分块抽取使用并发控制，默认并发数为 3，以平衡响应时间和模型服务压力。

易用性方面，前端应提供清晰的上传、列表和结果查看界面。对于 PDF 文档，若存在 bbox 信息，应支持点击结构化对象定位原文证据。
