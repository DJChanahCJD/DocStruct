# 第六章 系统测试

## 6.1 测试环境与数据集

### 6.1.1 测试环境

系统测试在云端 API 调用环境下进行，具体配置如下：

- **操作系统**：Windows 11
- **Python 版本**：3.11+
- **LLM 服务**：通过 OpenAI 兼容 API 调用，主要测试模型包括 Qwen（通义千问 Doc-Turbo）、DeepSeek（DeepSeek-V3）和 Moonshot（Kimi）
- **API 参数**：temperature=0.0，max_tokens=16384
- **分块配置**：chunk_max_chars=5000，overlap_chars=200，concurrency=3

### 6.1.2 数据集

测试数据集由多份中文软件工程文档组成，涵盖六种文档类型。每份文档配有由人工标注的真实数据（Ground Truth, GT），标注格式与系统输出的 Pydantic 模型一致。数据集通过 `experiments/manifest.json` 清单文件管理，将每份待测文档映射到对应的 GT 文件路径。

## 6.2 评估指标设计

系统采用信息检索领域的标准指标体系——精确率（Precision, P）、召回率（Recall, R）和 F1 分数（F1-Score），按槽位粒度进行评估。

### 6.2.1 对象匹配算法

评估的第一个关键问题是：如何判断系统预测的某个提取对象与 GT 中的某个标注对象是"同一个"对象？本系统采用基于名称相似度的贪婪匹配算法：

**名称归一化**。对预测对象和 GT 对象的 `name` 字段进行预处理：去除括号内的补充信息（如"（用户模块）"），统一全角/半角标点，转换为小写。

**词级二元组 Jaccard 相似度**（Word Bigram Jaccard）。本系统选用词级二元组（Bigram）而非字符级作为相似度计算的基本单位。对于两个字符串 a 和 b，分别提取其词级别的二元组集合（相邻两个词组成的对），计算 Jaccard 相似度：`J(A, B) = |A ∩ B| / |A ∪ B|`。词级二元组相比字符级能更好地捕捉语义相近但措辞略有差异的短语（如"用户管理模块"与"用户管理"）。

**类型模糊权重**。对于容易混淆的类型对（如 `system`/`data`、`functional`/`non_functional`、`http`/`rpc`），系统在计算匹配分数时引入类型模糊权重（默认 0.5~0.7）。当两个对象的名称相同但类型属于易混淆对时，匹配分数乘以模糊权重而非直接归零，从而避免因类型标注的细微差异导致整个对象被误判为不匹配。

**贪婪匹配**。对每个槽位，计算预测对象与 GT 对象两两之间的匹配分数，按分数从高到低进行贪心匹配。每个 GT 对象最多被匹配一次，匹配分数低于阈值（默认 0.35）的配对被丢弃。未匹配的预测对象计入假正例（FP），未匹配的 GT 对象计入假负例（FN），成功匹配的配对计入真正例（TP）。

### 6.2.2 指标计算

对于每个槽位 s：

$$P_s = \frac{TP_s}{TP_s + FP_s} \quad R_s = \frac{TP_s}{TP_s + FN_s} \quad F1_s = \frac{2 \cdot P_s \cdot R_s}{P_s + R_s}$$

全局指标按所有槽位的 TP/FP/FN 合计值计算 micro-average（微平均），同时计算 macro-average（宏平均，即各槽位指标的直接平均）以评估系统在所有槽位类型上的平均表现。

## 6.3 模型对比实验

模型对比实验旨在比较不同 LLM 在软件工程文档结构化提取任务上的表现差异。实验选取三种主流中文 LLM 服务：

- **Qwen Doc-Turbo**（阿里云通义千问）：专为文档理解任务优化的模型，具备原生长文档处理能力。
- **DeepSeek-V3**（深度求索）：通用大语言模型，在中文 NLP 任务上表现突出。
- **Kimi**（月之暗面 Moonshot）：以长上下文处理见长的通用模型。

实验在同一数据集上以相同配置运行，统一使用 `temperature=0.0` 以确保可复现性。评估结果按槽位统计 P/R/F1，并生成每个文档的详细匹配报告（包含每个预测-GT 配对的匹配分数和类型信息）。

## 6.4 消融实验

消融实验（Ablation Study）旨在评估管道中各可选组件对最终提取质量的贡献。实验设计了以下消融条件：

**（1）Phase 0 预扫描消融**。在关闭 Phase 0 预扫描的条件下运行管道，对比开启/关闭预扫描时的全局 F1 分数，评估文档级预扫描对分块提取一致性的影响。

**（2）Finalizer 消融**。在关闭 Finalizer 的条件下运行管道（即分块结果直接进入 Reducer），对比开启/关闭 Finalizer 时的槽位级指标，评估 LLM 二次合并对跨分块实体对齐的贡献。

**（3）重叠窗口消融**。将分块重叠字符数设置为 0，对比有/无重叠时的指标，评估上下文连续性对 LLM 提取质量的影响。

### 6.5.1 模型对比分析

通过对比三种模型的整体 F1 分数，可以评估专用文档模型与通用模型在结构化提取任务上的性能差异。预期 Qwen Doc-Turbo 在实体和接口槽位上具有优势（受益于其文档理解优化），而 DeepSeek-V3 和 Kimi 可能在长文本理解上表现更均衡。

评估报告同时分析不同槽位类型的提取难度差异。一般来说，`entities` 槽位（实体对象）因结构简单、数量适中，提取精度最高；`interfaces` 槽位（接口对象）因字段较多（http_method、endpoint、provider、consumer 等），对 LLM 输出格式的精确性要求更高，通常召回率偏低；需求类槽位因文本描述较长且语义复杂，精确率和召回率均面临挑战。

### 6.5.2 消融实验分析

Phase 0 预扫描对跨分块实体一致性应有正向贡献，尤其在文档类型特征不明显或关键实体分散在多个分块中的情况下。Finalizer 可能在某些文档类型上显著减少跨分块重复，但也可能引入新的合并错误。重叠窗口对跨分块边界处的信息连续性至关重要，关闭重叠预期会导致边界处实体的召回率明显下降。

### 6.5.3 错误分析

评估脚本生成的匹配报告可进一步用于定性错误分析，主要错误类型包括：

**名称表述差异**：预测对象与 GT 对象表述不同但语义相同（如"用户登录模块" vs "登录模块"），Jaccard 相似度偏低导致未匹配。

**槽位错配**：对象被提取到了错误的槽位（如将接口对象误放入实体槽位），这种跨槽位错误在当前的按槽位独立评估框架下被双倍惩罚（既计入假正例又计入假负例）。

**粒度假象**：预测将 GT 中的一个复合对象拆分为多个子对象，或反之将多个独立对象合并为一个。当前评估框架对粒度差异敏感，可能在精确率和召回率上双双产生惩罚。
