# 第五章 系统测试

## 5.1 测试目标

系统测试的目标是验证 DocStruct 是否能够完成从文档上传到结构化结果展示的核心流程，并通过离线评测框架评估大语言模型在软件工程文档结构化抽取任务中的实际效果。测试重点包括文件解析正确性、分块与抽取流程完整性、结果合并与证据绑定准确性，以及模型在各类文档类型上的表现。

## 5.2 功能测试

功能测试覆盖系统主流程和边界场景，验证各接口和模块的正确性。

## 5.3 离线评测设计

### 5.3.1 评测框架

项目提供 `scripts/evaluate.py` 作为离线评测脚本，支持两种模式：离线模式读取 `experiments/results/cached` 中的缓存抽取结果，用于快速复现已有实验；在线模式通过 `--live` 参数实时调用 LLM 抽取并写入缓存，用于验证不同模型或参数下的表现。评测脚本支持通过 `--doc` 和 `--gt` 参数指定单文档评估，也支持通过 `--manifest` 执行批量评估。

评测数据集包含 6 份中文软件工程文档样本，每份文档有对应的人工标注 Ground Truth JSON。

表 5-2 评测数据集

| 文档 | 类型 | GT 对象数 | 说明 |
| --- | --- | ---: | --- |
| experiments/assets/srs_mini.pdf | srs | 18 | 短篇需求规格说明书，含功能需求、非功能需求和目标用户 |
| static/examples/srs_example.md | srs | 52 | 中篇需求规格说明书，含完整业务流程 |
| experiments/assets/api_mini.md | api | 3 | 短篇 API 文档 |
| static/examples/api_example.md | api | 17 | 中篇 API 文档，含请求参数和错误码 |
| static/examples/test_case_example.md | tc | 10 | 测试用例文档 |
| experiments/assets/design_mini.md | hld | 8 | 概要设计文档，含模块、流程和设计决策 |

### 5.3.2 评估指标与方法

评测以 typed schema 为口径，动态发现 GT 和预测结果中的 list 类型槽位，按槽位计算匹配指标。对象匹配采用名称词级 bigram Jaccard 相似度、子串包含优先和类型字段模糊权重相结合的贪心匹配算法。匹配阈值设为 0.3。匹配完成后统计各槽位的 TP（正确匹配）、FP（多余预测）和 FN（遗漏对象），计算 Precision、Recall 和 F1。

评估维度参考 Ragas 的忠实度与上下文相关性思路[8]以及 ALCE 的引用质量评估框架[7]。具体匹配策略为：接口对象优先按 HTTP 方法和路径精确匹配，模块和流程对象按名称相似度匹配，普通对象使用归一化名称加类型权重综合匹配。名称中的括号后缀（如"用户注册（SRS-USER-001）"）在匹配前自动剥离，以消除命名格式差异的影响。

## 5.4 单模型评测结果

本节使用 DeepSeek-V4-Flash 作为抽取模型，在评测数据集的 6 份文档上运行在线评测。

### 5.4.1 整体结果

表 5-3 各文档评测结果汇总

| 文档 | 类型 | Precision | Recall | F1 | TP | FP | FN |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| api_mini | api | 1.000 | 1.000 | 1.000 | 3 | 0 | 0 |
| api_example | api | 1.000 | 1.000 | 1.000 | 17 | 0 | 0 |
| srs_mini | srs | 1.000 | 0.611 | 0.759 | 11 | 0 | 7 |
| srs_example | srs | 0.955 | 0.808 | 0.875 | 42 | 2 | 10 |
| design_mini | hld | 0.875 | 0.875 | 0.875 | 7 | 1 | 1 |
| test_case_example | tc | 0.900 | 0.900 | 0.900 | 9 | 1 | 1 |
| **总计** | — | **0.957** | **0.864** | **0.908** | **89** | **4** | **19** |

在 6 份测试文档上，DeepSeek-V4-Flash 的整体 F1 达到 0.908（Precision=0.957, Recall=0.864）。API 文档抽取表现最佳，两份 API 文档均达到 F1=1.000，所有接口对象被正确识别且无多余预测。SRS 文档和 HLD 文档表现中等，F1 在 0.76-0.88 之间。测试用例文档 F1 为 0.900。

系统的 Precision 总体较高（0.957），说明模型输出质量较好，几乎不存在编造对象的问题。Recall 相对较低（0.864），主要受 SRS 文档中部分槽位未被模型输出的影响。

### 5.4.2 按槽位分析

表 5-4 各槽位评测明细

| 槽位 | 文档数 | 总 GT | Precision | Recall | F1 |
| --- | ---: | ---: | ---: | ---: | ---: |
| apis | 2 | 20 | 1.000 | 1.000 | 1.000 |
| functional_requirements | 2 | 17 | 1.000 | 1.000 | 1.000 |
| non_functional_requirements | 2 | 38 | 1.000 | 0.868 | 0.930 |
| modules | 1 | 4 | 1.000 | 1.000 | 1.000 |
| core_flows | 1 | 1 | 1.000 | 1.000 | 1.000 |
| test_cases | 1 | 10 | 0.900 | 0.900 | 0.900 |
| design_decisions | 1 | 3 | 0.667 | 0.667 | 0.667 |
| target_users | 2 | 6 | 0.600 | 0.500 | 0.545 |
| business_flows | 2 | 9 | — | 0.000 | 0.000 |

API 接口抽取达到完美匹配（F1=1.000），说明模型对接口路径、HTTP 方法和参数的识别能力成熟。功能需求抽取同样达到完美匹配（F1=1.000），需求名称和要点的识别准确。非功能需求抽取 Precision=1.000 但 Recall=0.868，5 个 FN 主要来自 srs_example 中部分属性类需求的漏提。

需要关注的问题是 business_flows（业务流程）槽位在两份 SRS 文档上均未被模型输出。分析发现当前 Prompt 中对该槽位的描述不够明确，模型倾向于将流程步骤合并入功能需求而非独立输出为业务流对象。target_users 槽位同样存在识别不稳定的问题——srs_mini 中完全遗漏，srs_example 中有 3/3 的召回但有 2 个多余预测。design_decisions 的 F1 较低（0.667）是因为部分设计决策在原文中分散于不同段落，模型未能完整聚合。

### 5.4.3 误差分析

FP（多余预测）共 4 个，分布在 srs_example 的 target_users（2 个，模型将"产品经理"和"测试人员"额外输出但 GT 未标注）、test_case_example（1 个，测试步骤粒度差异导致匹配失败）和 design_mini（1 个，设计决策表述差异）。

FN（遗漏对象）共 19 个，主要来源为 business_flows（9 个，全槽位遗漏）和 target_users（3 个，srs_mini 全槽位遗漏）。其余 7 个分布在 non_functional_requirements（5 个，部分属性类需求未被独立抽取）、design_decisions（1 个）和 test_cases（1 个）。

这些结果表明当前系统在结构清晰的对象（接口、功能需求、模块）上表现良好，但在需要跨段落聚合语义的对象（业务流程、设计决策）和建模较弱的槽位（target_users）上仍有改进空间。改进方向包括优化 Prompt 中 business_flows 和 target_users 的槽位描述、在分块中为这些槽位增加明确示例，以及调整分块策略使跨段落关联信息不丢失。

## 5.5 模型选择实验

为选择适合本系统的默认大语言模型，在相同数据集、相同 Prompt 和相同分块参数下对三个候选模型进行对比评测。

表 5-5 模型对比结果

| 维度 | qwen-doc-turbo | deepseek-v4-flash | kimi-k2.5 |
| --- | ---: | ---: | ---: |
| JSON 合法率 | 95.8% | 98.3% | 96.2% |
| 整体 F1 | 0.861 | 0.908 | 0.879 |
| 平均耗时（秒） | 17.3 | 20.2 | 24.1 |
| 成本评价 | 低 | 较低 | 高 |

从实验结果看，三个模型均能稳定输出合法 JSON（95% 以上），DeepSeek-V4-Flash 在 F1 上明显优于 qwen-doc-turbo 和 kimi-k2.5，同时成本显著低于 kimi-k2.5，在中文软件工程文档场景中表现最佳。综合考虑以下因素，本文选定 DeepSeek-V4-Flash 作为系统默认模型：第一，DeepSeek-V4 系列模型在百万 Token 上下文、混合注意力和流形约束超连接等架构创新方面表现突出，V4-Flash 在多项中文 NLP 评测中达到领先水平[14]；第二，DeepSeek 模型已适配国产昇腾等 AI 芯片，应用前景更广；第三，DeepSeek 官方 API 支持结构化输出（JSON Mode），与本文 typed schema 思路天然契合，且提供缓存命中折扣机制，实际使用成本更低。

当前系统运行配置中环境变量 `LLM_MODEL` 默认值为 `qwen-doc-turbo`，部署时可通过环境变量覆盖为 `deepseek-v4-flash`，或在 `.env` 文件中直接修改默认值。

## 5.6 测试结论

综合功能测试和离线评测结果，DocStruct 已经形成从文档上传、解析、分块抽取、结果合并到证据回馈的完整闭环。系统能够正确解析多格式文档，按文档类型执行 typed schema 抽取，并将结构化结果与原文证据关联。使用 DeepSeek-V4-Flash 模型的整体 F1 达到 0.908，API 文档和功能需求抽取接近完美。

当前评估仍存在局限性：评测数据集仅 6 份文档，覆盖的文档类型和复杂程度有限；部分槽位（business_flows、target_users）的系统性遗漏有待通过 Prompt 优化改进。后续应扩大数据集规模，补充数据库设计文档和更多真实项目文档，并对不同文档类型分别报告细粒度指标。
