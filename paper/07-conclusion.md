# 第七章 结论

## 7.1 工作总结

本文围绕"如何高效、准确地从多种软件工程文档中提取结构化信息并建立证据追溯"这一核心问题，设计并实现了 DocStruct——基于大模型的软件工程文档内容结构化提取系统。主要完成了以下工作：

**（1）多格式文档统一解析管道。** 实现支持 PDF、DOCX、Markdown 和纯文本四种格式的统一解析，通过策略模式组织解析器，将异构格式转化为一致的 Markdown 中间文本表示。PDF 解析器内置 OCR 智能检测机制，在保证解析质量的同时避免不必要的 OCR 开销。

**（2）文档类型专用提取架构。** 定义六种软件工程文档类型（SRS、API 设计、系统设计、测试文档、用户手册、问题/缺陷单）的 Pydantic 提取模式，每种模式包含专用的输出槽位和类型化的提取项层次结构。通过 Phase 0 预扫描机制实现文档类型的自动识别，并通过 Schema Registry 实现文档类型到提取模型的动态映射。

**（3）Map-Reduce 长文档提取管道。** 设计并实现了分节感知分块策略，按章节边界组织文档元素并生成大小可控的分块；Map 阶段通过受限并发调用 LLM 对各分块进行局部提取，Reduce 阶段通过确定性算法完成跨分块合并、身份去重和全局 ID 分配。管道支持可选 Phase 0 预扫描和 Finalizer 二次合并。

**（4）证据绑定与可验证回溯。** 实现了从提取对象到源文档元素的完整证据链。分块阶段为每个文档元素注入位置标记，LLM 提取阶段要求引用对应标记，Reducer 阶段交叉验证引用有效性并构建证据记录。前端通过 PDF.js 边界框叠加层实现证据的可视化展示。

**（5）完整的端到端系统与评估框架。** 构建了包含 FastAPI 后端、React 前端、SQLite 数据库的完整 Web 应用，支持文档上传、解析、提取、校对和手动修订的全流程。设计了离线评估框架，支持多模型对比实验和消融实验，按槽位粒度计算 P/R/F1 指标。

## 7.2 创新点归纳

本文工作的主要创新点可归纳为以下三个方面：

**（1）面向软件工程文档的多类型专用提取架构。** 区别于将 LLM 输出定义为通用 JSON 的简单做法，本系统为每类软件工程文档设计了专用的 Pydantic 模式，包含该类型特有的语义槽位和字段约束。这种"类型化模式"设计使得提取结果在结构上具有强保证，也使得前端可以按槽位组织差异化的展示和编辑界面。

**（2）Map-Reduce 管道与证据绑定相结合的处理范式。** 现有 LLM 提取系统通常面临两难选择：要么在全量上下文中一次性提取（受窗口大小限制且缺乏可验证性），要么在分块提取后丢弃溯源信息。本系统通过 Map-Reduce 管道将 LLM 的语义能力限定在局部上下文，通过证据绑定机制保留每个提取对象与源文档之间的溯源关联，并通过确定性 Reducer 消除跨分块的不一致性。这种"局部 LLM + 全局确定性归约 + 证据追溯"的设计模式兼顾了提取覆盖率和结果可靠性。

**（3）端到端实证评估。** 与许多止步于概念验证的学术工作不同，本系统构建了完整的在线服务和离线评估基础设施，能够对多种 LLM 模型、多个管道组件进行系统的定量对比和消融分析，为 LLM 在软件工程文档结构化提取领域的应用提供了可复现的实证数据基础。

## 7.3 不足与展望

本系统仍存在以下不足，为未来改进指明了方向：

**（1）异步处理体验。** 当前系统采用轮询机制（前端每 2 秒查询一次文档状态）实现异步处理的进度反馈。更理想的方案是引入 WebSocket 或 Server-Sent Events（SSE）推送，将分块提取的实时进度（已完成分块数/总块数）推送到前端，提供更流畅的用户体验。

**（2）多轮交互式提取。** 当前管道是单次执行模式——用户上传文档后获得一次提取结果。更高阶的交互模式应是"多轮校对"：用户可以在提取结果中标注意见后触发针对性重新提取，LLM 根据用户反馈仅修改被标注的问题字段，而非全量重新处理。

**（3）人工审核闭环。** 系统当前支持人工修订，但修订数据未被系统性地反馈到评估和改进管道。未来可以通过收集用户修订记录构建持续改进的数据飞轮：将修订后的数据作为增量训练样本，用于提示词优化或模型微调。

**（4）评估框架扩展。** 当前的评估框架以名称匹配为核心，对粒度差异和槽位错配的容忍度有限。未来可引入基于语义向量（Embedding）的软匹配策略，并通过多标注者一致性分析（Inter-Annotator Agreement）评估 GT 数据的标注质量。
