# 第三章 需求分析

## 3.1 系统目标与范围

DocStruct 系统的核心目标是实现单文档级别的软件工程文档结构化提取与评测。系统接收用户上传的软件工程文档（PDF、DOCX、Markdown 或纯文本），自动完成格式解析、文档类型识别、结构化信息提取，并将提取结果以类型化的 JSON 格式提供给用户下载或在前端界面中交互式浏览。

系统的功能边界明确限定在"单文档结构化抽取"，明确排除以下范围：跨文档知识图谱构建、需求追踪矩阵自动生成、代码-需求-测试自动关联、向量检索与知识库问答、URL 导入和多模型实时切换。这些边界的划定基于以下考虑：单文档场景是软件工程文档处理的最小完备单元，本课题聚焦于验证 LLM 在该场景下的提取能力边界，而跨文档关联和知识管理属于更上层的高级功能，可在本系统的输出基础上进一步构建。

## 3.2 功能性需求

系统应具备以下核心功能：

**（1）文档上传。** 用户可通过 Web 界面上传 PDF、DOCX、TXT 或 Markdown 格式的软件工程文档，并指定文档类型（SRS、API 设计、系统设计、测试文档、用户手册、问题/缺陷单或未知类型）。上传接口在接收文件后立即返回响应，后续的解析和提取任务在后台异步执行。

**（2）文档解析。** 系统根据文件扩展名自动选择合适的解析器（PDF → PdfParser、DOCX → DocxParser、TXT/MD → PlainTextParser），将二进制或标记格式文档转化为统一的 Markdown 中间文本表示。支持可选的 OCR 模式（用于扫描型 PDF）和替代解析后端（基于 Docling）。

**（3）文档类型指定。** 系统支持六种主流软件工程文档类型，每种类型拥有独立的提取模式（Schema）：软件需求规格说明书（SRS）、接口文档（API）、系统设计文档（Design）、测试文档（Test）、用户手册（Manual）、问题/缺陷单（Issue）。当用户选择"未知类型"时，系统仅执行解析，不进行结构化提取。

**（4）结构化提取。** 系统采用 Map-Reduce 管道对已解析文档进行结构化信息提取：在 Map 阶段，将文档按章节边界分块，并发调用 LLM 对各分块进行局部提取；在 Reduce 阶段，通过确定性算法合并分块结果、去重并分配全局 ID。支持可选的 Phase 0 预扫描（用于自动识别文档类型和关键实体）和 Finalizer 阶段（LLM 二次合并）。

**（5）Schema 校验。** 所有 LLM 提取结果必须通过对应文档类型的 Pydantic 模型校验。校验失败的字段或对象触发明确的错误信息，不会被静默保存。系统对 LLM 返回的原始 JSON 进行健壮解析，能处理 Markdown 代码块包裹、JSON 截断和 Python 风格单引号等常见异常格式。

**（6）证据绑定。** 每个提取出的结构化对象都应绑定到原始文档中的对应位置，包括元素 ID、页码和边界框坐标（若可用）。用户可在前端界面点击任意提取对象，直接导航到原始文档的对应位置查看高亮标记。

**（7）结果查看与修订。** 系统提供 Web 前端界面，按文档类型特定的槽位分组展示提取结果。用户可查看提取字段、对应的原文证据，并对提取结果进行人工修订后保存。

**（8）离线评测。** 系统提供离线评估脚本，将提取结果与人工标注的真实数据（Ground Truth）进行对比，计算每个槽位的精确率（Precision）、召回率（Recall）和 F1 分数，生成 JSON 和 Markdown 格式的评估报告。

## 3.3 非功能性需求

**（1）结构稳定性。** 所有提取输出必须通过对应的 Pydantic Schema 校验，不合法结构不得入库。这是系统的核心质量保障机制。

**（2）长度限制。** 默认最大处理文档长度为 100,000 字符。超出此限制的文档应被明确拒绝并返回错误提示，避免产生高额 API 费用或超长处理延迟。

**（3）并发控制。** LLM 调用采用受限并发策略（默认并发数为 3），通过 `asyncio.Semaphore` 控制，避免超出 API 速率限制。

**（4）可扩展性。** 新增文档类型和提取模式应通过扩展 Pydantic 模型和 Schema Registry 实现，不需要修改核心管道代码。

**（5）错误处理。** 管道各阶段应具备容错能力。单个分块提取失败不应阻塞其他分块的处理；Finalizer 失败时应回退到确定性 Reducer；LLM 返回非法 JSON 时应进行健壮解析而非直接崩溃。

## 3.4 文档类型定义

系统将软件工程文档按其结构和内容特征划分为六种类型，每种类型对应一个专用的提取模式（Extraction Schema）。表 3-1 列出了六种类型的定义和核心提取槽位。

**表3-1 支持的文档类型及其提取槽位**

| 文档类型 | 代码 | 核心槽位 | 用途场景 |
|---------|------|---------|---------|
| 软件需求规格说明书 | srs | entities, functional_requirements, non_functional_requirements, interfaces | 系统/软件需求的结构化整理 |
| 接口文档 | api | entities, endpoints, schemas, auth | API 接口定义的结构化提取 |
| 系统设计文档 | design | entities, modules, interfaces, decisions | 系统设计方案的结构化整理 |
| 测试文档 | test | entities, test_cases, test_steps, defects | 测试用例与缺陷的结构化提取 |
| 用户手册 | manual | entities, procedures, ui_elements, notes | 用户操作说明的结构化提取 |
| 问题/缺陷单 | issue | entities, symptoms, reproduction_steps, environment | 问题报告的结构化提取 |

每种提取模式定义了 3-4 个核心槽位，这些槽位覆盖了该文档类型中最具价值的结构化信息维度。在所有类型中，`entities` 槽位（实体对象）是共有的，用于抽取文档中涉及的参与者、系统、模块和数据对象。

## 3.5 数据需求

系统的核心数据结构包含三个层次：

**（1）原始文件信息。** 包括文件名、存储路径、上传时间和用户指定的文档类型。这是系统处理链的起点。

**（2）解析结果。** 包括规范化后的 Markdown 文本和 Document IR（含文档元素列表、章节大纲和元数据）。解析结果被持久化到数据库，支持复用——用户可修改解析内容后触发重新提取，无需重复上传文件。

**（3）提取结果。** 以 JSON 格式存储的结构化数据，包含按槽位组织的提取对象（含系统分配的全局 ID、名称、类型、详细字段和证据引用）以及证据列表（含对象 ID、源元素 ID、文本片段、页码和边界框坐标）。提取结果以数据库 JSON 字段形式存储，方便前端直接查询和展示。

数据库仅存储文档记录和提取结果，不建立知识图谱或向量索引，不进行跨文档关联。这种设计保证了系统的轻量级部署（单 SQLite 文件即可运行）和数据模型的简洁性。
