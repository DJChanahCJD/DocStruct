# 基于大模型的软件工程文档结构化提取系统

**汇报人：陈大钧｜日期：2026-04-17**

---

## 问题与价值

软件工程文档（SRS、API 文档、测试报告等）普遍以非结构化形式存储，传统提取手段存在明显局限：

| 方法 | 局限 |
|------|------|
| 关键词匹配 | 无法理解语义，漏召回多 |
| 正则规则 | 格式强依赖，脆弱易崩 |
| NLP 模型 | 抽取复杂结构能力不足 |

**大模型方案示例：**

> 输入："系统应该允许管理员删除用户账户。"
>
> 输出：
>
> ```
>   {
>       "id": "REQ-001",
>       "title": "允许管理员删除用户账户",
>       "category": "functional"
>    }
> ```

**项目定位：** 将非结构化软件工程文档转化为**可检索、可复用、可问答**的结构化数据，服务于 AI 编程辅助、研发协作、知识库等场景。

## 系统设计

```mermaid
flowchart LR
    A[文档输入<br/>PDF / DOCX / MD / TXT] --> B[解析预处理成 Markdown]
    B --> C[文档分类<br/>]
    C --> D[结构化抽取<br/>LLM+Schema]
    D --> E[存储与检索<br/>SQLite+FAISS]
    E --> F[RAG问答]
```

### 技术栈

| 层次       | 技术                                                         |
| ---------- | ------------------------------------------------------------ |
| 后端       | `FastAPI` + `Tortoise-ORM` + `SQLite`                        |
| 文档解析   | `pymupdf4llm`（PDF）、`python-docx`（DOCX）、 原生读取（MD / TXT） |
| 结构化抽取 | OpenAI-Compatible API + `Pydantic`（Schema 约束）            |
| 向量检索   | `Embedding`（语义向量化）+ `FAISS`（向量索引）+ `NumPy`（向量计算） |
| 前端       | `React` + `TypeScript` + `Vite` + `shadcn/ui`                |

### **关键设计**

* 支持多模型切换（统一使用[阿里百炼平台](https://bailian.console.aliyun.com/cn-beijing?tab=model#/model-market/all)的模型：`qwen-turbo-doc` / `deepseek-v3.2` / `kimi-2.5`）
| 模型 | 输入价 | 输出价 | 上下文 | 定位 | 最大输入/输出长度 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| DeepSeek-V3.2 | 2 | 3 | 128K | 推理/代码/思考 | 96K/64K |
| Kimi-K2.5 | 4 | 21 | 256K | 长文本/多模态 | 224K/16K |
| [Qwen-Doc-Turbo]([文件数据挖掘生成结构化数据-数据挖掘（Qwen-Doc）-大模型服务平台百炼-阿里云](https://help.aliyun.com/zh/model-studio/data-mining-qwen-doc)) | 0.6 | 1 | 256K | 文档精读/长文本 | 248K(文件上传支持最大20万字文档，但纯文本仅9K）/8K |

* 两阶段处理：
  * 分类：调用`qwen-doc-turbo`截取前2000字符，快速判断文档类型。
  
  * ```
    # 分类 prompt
    You are an expert in software engineering documentation. Classify the following document summary into one category.
    
    Document Summary:
    {summary}
    
    Categories:
    srs: Software Requirements Specification
    api: API documentation
    design: System or architecture design
    ...
    unknown: None of the above
    
    Return JSON:
    {{
      "doc_type": "srs | api | design | test_plan | test_case | test_report | user_manual | bug_report | unknown",
      "confidence": 0.0-1.0
    }}
    ```
    
  * 抽取：通过 Pydantic 将对应文档类型的 JSON Schema 注入Prompt，调用LLM，并校验输出结果。
  
  * ```
    # 结构化提取 Prompt
    Extract structured information from the following Markdown document using the provided JSON Schema.
    
    Document:
    {content}
    
    Schema:
    {schema}
    ```
  
* 长文档分块（每5k字+200字用于重叠定位） + 结果合并  +  回退机制（直接传入完整文档）

## 文档类型设计

支持八种软件工程文档：

| 文档类型 | `doc_type` |
| --- | --- |
| 软件需求规格说明书 | `srs` |
| API 接口文档 | `api` |
| 系统设计说明书 | `design` |
| 测试计划 | `test_plan` |
| 测试用例 | `test_case` |
| 测试报告 | `test_report` |
| 用户手册 | `user_manual` |
| 缺陷报告 | `bug_report` |

**统一结构：**

```json
{
  "doc_type": "",   // 文档类型（srs/api/...）
  "title": "",      // 文档标题
  ...,              // 标准字段（按类型定义）
  "extra": {}        // 非标准扩展字段
}
```

例如：需求规格说明书（SRS）
```json
{
  "doc_type": "srs",
  "title": "需求规格说明书",
  "version": "1.0",
  "overview": "本文档描述用户管理系统的功能需求",
  "requirements": [
    {
      "id": "REQ-001",
      "title": "删除用户功能",
      "description": "用户应该允许管理员删除用户账户",
      "priority": "high",
      "category": "functional"
    },
    {
      "id": "REQ-002",
      "title": "用户登录功能",
      "description": "用户可以通过用户名和密码登录系统",
      "priority": "high",
      "category": "functional"
    }
  ],
  "extras": {}
}
```

## 实验设计

### 实验一：选最优配置

**目标：** 对比模型与 Prompt 效果

**数据：** 6个 文档（短3 / 中2 / 长1）

**变量：**

- 模型：qwen / deepseek / kimi
- Prompt：中英文、简短/详细（角色与否）

**评测：** 标准答案 + LLM评审

**指标：**

- 抽取准确率
- 字段完整率
- 耗时

------

### 实验二：验证类型泛化

**目标：** 验证最优配置对8类文档的覆盖能力

**数据：** 8类文档 × 各1（中等长度）

**变量：** 文档类型

**评测：** 标准答案 + LLM评审

**指标：**

- 抽取准确率
- 字段完整率

------

### 实验三：验证鲁棒性

**目标：** 验证系统在复杂场景下的稳定性与边界表现

**数据：** 12–16个文档（复用实验二 + 扩展样本）

**变量：**

- 格式：MD / Word / PDF / TXT
- 语言：中 / 英 / 混合
- 质量：标准 / 非标准
- 长度：短 / 中 / 长

（仅覆盖，不做全组合）

**评测：** 标准答案 + LLM评审

**指标：**

- 抽取准确率
- 字段完整率



## 主要问题


1. 长文档处理慢：分块+串行调用导致耗时高，且合并块时存在信息丢失风险
2. 文档提取字段混乱且不够细化，暂时无法覆盖大多数工程场景
3. 图片型 PDF 文档暂时无法处理，需要引入 OCR
4. 缺乏真实软件工程文档
