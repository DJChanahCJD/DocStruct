> 核心目标：单文档软件工程文档结构化抽取与评测，不做“跨文档知识图谱、需求追踪矩阵、代码-需求-测试自动关联”
1. 项目目标

DocStruct 面向软件工程文档的结构化提取场景，支持将 PDF、DOCX、MD、TXT 等格式文档解析为 Markdown，并调用大模型抽取为统一 JSON 结构。系统重点解决软件工程文档内容非结构化、字段不统一、人工整理成本高、抽取结果难校验的问题。

2. 功能性需求

系统应支持文档上传、文档解析、文档类型指定、结构化抽取、Pydantic 校验、结果存储、详情查看、人工修订和离线评测。

系统支持的文档类型包括：

srs：软件需求规格说明书
api：接口文档
design：系统设计文档
test：测试文档
manual：用户手册
issue：问题单/缺陷单
unknown：未知类型，仅解析原文，不执行结构化抽取

结构化输出统一使用六类主槽位：

entities      实体对象，如角色、模块、系统、数据对象
processes     流程对象，如业务流程、操作步骤、测试步骤
requirements  需求对象，如功能需求、非功能需求、约束、验收条件
interfaces    接口对象，如 HTTP 接口、外部系统对接、文件交换
artifacts     文档产物，如测试用例、手册章节、缺陷项、设计模块
metrics       指标对象，如响应时间、并发数、可用性、通过率
3. 非功能性需求

系统应保证抽取结果结构稳定，能够通过 Pydantic Schema 校验。系统仅面向中短文档，默认最大处理长度为 100000 字符。超过阈值的文档直接拒绝处理。

系统应支持固定分块抽取策略，长文档按照固定大小分块并发调用大模型，再合并为统一结构。系统应保留 source_ref，支持抽取条目回溯到原文片段、页码或章节。

4. 数据需求

系统主要存储三类数据：

原始文件信息：文件名、路径、上传时间、文档类型、处理状态
解析结果：Markdown / 文本内容
抽取结果：符合统一 Pydantic Schema 的 JSON 数据

数据库只存储文档记录和抽取结果，不拆分建立知识图谱节点表或关系表。

5. 系统边界

系统不包含：

知识库问答
向量检索
URL 导入
多模型切换
前端复杂联动
跨文档知识图谱构建
复杂关系抽取

这些能力如需扩展，应作为独立模块重新设计。
